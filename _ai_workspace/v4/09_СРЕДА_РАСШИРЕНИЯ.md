## Инцидент: 429 при установке vitest.explorer
- Симптом: `Error while installing extension vitest.explorer: Server returned 429` (временный лимит магазина при подряд идущих установках).
- Решение: пауза ~2 минуты и повтор — установилось из магазина. Запасной путь (не понадобился): .vsix с open-vsx.org/api/vitest/explorer/latest -> `--install-extension <файл.vsix>`.
- Урок: при установке нескольких расширений подряд делать паузы; при 429 просто подождать и повторить.

## Windows-MCP с whitelist (этап 13, 28.11.2026)

Прецедент: desktop-automation MCP подключён в user scope с урезанным набором инструментов; доказательство — Блокнот с напечатанной строкой «Привет от Windows-MCP» (скриншот показан в сессии, файл не сохранялся).

- Python: `uv python install 3.14` → установлен `cpython-3.14.10-windows-x86_64-none`; `windows-mcp 0.9.0` требует Python `>=3.14`.
- Конфиг: `%APPDATA%\Devin\mcp_config.json`, сервер `windows-mcp`, команда `uvx`, аргументы `--with opencv-python windows-mcp serve --tools Screenshot,Snapshot,Click,Type,Scroll,App`, transport `stdio`.
- Безопасность: агенту видны только `App`, `Snapshot`, `Screenshot`, `Click`, `Type`, `Scroll`; `PowerShell`, `Registry`, shell/file-system инструменты отсутствуют. Нюанс: сервер дополнительно экспортирует мета-инструмент `ControlStatus` даже при `--tools`, поэтому в Devin-config добавлен `disabledTools: ["ControlStatus"]` для строгого whitelist на стороне клиента.
- Зависимость-ловушка: в `windows-mcp 0.9.0` `opencv-python` не объявлен в `Requires-Dist`, но `Screenshot` импортирует `cv2` и падает `No module named 'cv2'`. Рабочий обход — `uvx --with opencv-python windows-mcp ...` (зависимость живёт только в ephemeral uvx-окружении, не в системном Python).
- Блокнот Windows 11 — одно окно с вкладками: запуск `C:\Windows\System32\notepad.exe` может вернуть фокус в уже открытый пользовательский файл. Перед вводом обязательно проверять заголовок/вкладку через `Snapshot`; для демонстрации создана новая пустая вкладка «Без имени». Пользовательские вкладки не изменялись.
- `App launch_executable` с относительным `notepad.exe` ищет файл в текущей рабочей папке и падает; использовать полный путь `C:\Windows\System32\notepad.exe` или Start Menu mode.
- Защита control ownership реальная: при активности пользователя действие возвращает `USER_CONTROL` и ждёт `control-idle-timeout` (~10 сек). Это не сбой сервера; повторять только после паузы и заново сверять фокус, потому что за паузу пользователь мог свернуть/сменить окно.
